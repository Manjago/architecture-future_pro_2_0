# TCO-анализ трансформации «Будущее 2.0»

Сравнение совокупной стоимости владения (Total Cost of Ownership) текущей и целевой архитектуры на горизонте трёх лет.

## Допущения

**Единица измерения:** 1 у.е. = стоимость одного инженера в год (FTE). Используется для демонстрации структуры и пропорций затрат без привязки к абсолютным суммам.

**Масштаб компании:**
- Текущая IT-команда: ~15 инженеров (DBA, ESB-инженеры, PowerBuilder-разработчики, Python/Go-разработчики, DevOps, аналитики).
- Бизнес-аналитики, использующие отчётность: ~20 человек.
- Объём данных: сотни терабайт в DWH.

**Другие допущения:**
- Облачный провайдер выбран, базовые тарифы известны.
- Курсы валют и тарифы стабильны (чувствительность оценена отдельно).
- Найм новых специалистов возможен в разумные сроки (3–6 мес.).
- Лицензии SQL Server и Power BI — бессрочные, без расходов на продление, но без обновлений безопасности.

## TCO текущего состояния (as-is)

Стоимость поддержки текущей архитектуры на горизонте 3 лет **при условии, что ничего не меняется**.

### Ежегодные затраты

| Статья затрат | Год 1 | Год 2 | Год 3 | Комментарий |
|--------------|-------|-------|-------|-------------|
| **Инфраструктура** (on-premise) | 3.0 | 3.2 | 3.5 | Серверы, СХД, сетевое оборудование, ЦОД (аренда, электричество, охлаждение). Рост связан с увеличением объёма данных и износом оборудования. |
| **Лицензии** | 2.0 | 2.0 | 2.0 | SQL Server (бессрочная лицензия, но SA/поддержка), Power BI Pro, PowerBuilder runtime. |
| **Персонал** (поддержка) | 8.0 | 8.5 | 9.0 | 2 DBA (SQL Server), 1 ESB-инженер (Camel), 2 PowerBuilder-разработчика, 3 бэкенд-разработчика (Python, Go, Java). Рост: дефицит PowerBuilder-специалистов → рост зарплат; DBA для SQL Server 2008 тоже дорожают. |
| **Эксплуатация** (ops) | 2.0 | 2.2 | 2.5 | Мониторинг, бэкапы, инцидент-менеджмент, патчинг. Рост: стареющее оборудование → больше инцидентов, SQL Server 2008 без security patches → больше ручной работы по защите. |
| **Потери от неэффективности** | 3.0 | 3.5 | 4.0 | Время аналитиков на ожидание отчётов (часы), ручная сборка данных, невозможность self-service. Упущенная выручка от задержки запуска новых направлений (фарма, электроника). Рост: масштабирование без изменения архитектуры усугубляет проблемы. |
| **Итого as-is** | **18.0** | **19.4** | **21.0** | |

### Итого as-is за 3 года: **58.4 у.е.**

**Ключевое наблюдение:** стоимость as-is **растёт** год к году. Это не стабильная платформа, а деградирующая: оборудование стареет, специалисты дорожают, неэффективность нарастает с ростом данных и бизнес-направлений. SQL Server 2008 (end-of-life с 2019) — тикающая бомба: один серьёзный security-инцидент с медицинскими или финансовыми данными может стоить многократно больше всего TCO.

## TCO целевого состояния (to-be)

Стоимость перехода на целевую архитектуру и её эксплуатации. Включает проектные затраты на миграцию.

### Год 1 (0–12 месяцев): параллельная работа

Этап максимальных затрат. Legacy работает в полном объёме, параллельно строится новая архитектура, пилот в 1–2 доменах.

| Статья затрат | Сумма | Комментарий |
|--------------|-------|-------------|
| **Инфраструктура** (on-prem + облако) | 5.0 | Старое оборудование работает + облачная инфраструктура для пилота (managed Kafka, PostgreSQL, K8s, staging-среда). Двойные расходы. |
| **Лицензии** | 2.0 | Legacy-лицензии сохраняются. Облачные managed-сервисы входят в инфраструктуру. |
| **Персонал** (legacy + новое + обучение) | 13.0 | Legacy-команда сохраняется (~6 FTE). Новая команда (~4 FTE: Kafka, K8s, платформа). Обучение текущих сотрудников (~1 FTE в пересчёте на время). Найм 2–3 новых специалистов (~2 FTE с учётом рекрутинга и онбординга). |
| **Эксплуатация** (два мира) | 3.0 | Поддержка legacy + настройка мониторинга для новой инфраструктуры. Два набора алертов, два набора runbook-ов. |
| **Проектные затраты** (миграция) | 4.0 | Архитектурное проектирование, разработка Camel Bridge (ACL), тестовая миграция данных, нагрузочное тестирование, внешние консультанты (Kafka, DDD — менторинг на 3–6 мес.). |
| **Потери от неэффективности** | 2.0 | Снижаются: пилотные домены уже работают на новой архитектуре, но основная отчётность ещё через DWH. |
| **Итого Год 1** | **29.0** | |

### Год 2 (12–24 месяца): масштабирование

Критические домены мигрированы, Self-Service BI Portal запущен (MVP), legacy сокращается.

| Статья затрат | Сумма | Комментарий |
|--------------|-------|-------------|
| **Инфраструктура** (on-prem сокращается) | 4.0 | On-prem сокращается по мере миграции доменов. Облако растёт, но managed-сервисы дешевле собственного железа в расчёте на единицу производительности. |
| **Лицензии** | 1.5 | Power BI выводится (замена на Self-Service BI Portal). SQL Server ещё работает для оставшихся доменов. |
| **Персонал** | 11.0 | Legacy-команда сокращается (~3 FTE — только поддержка DWH и оставшихся маршрутов Camel). Новая команда вышла на скорость (~7 FTE). Обучение завершено. Часть бывших legacy-специалистов переквалифицирована. |
| **Эксплуатация** | 2.5 | Legacy-часть сокращается. Новая инфраструктура стабилизируется, runbook-и написаны. |
| **Проектные затраты** (миграция) | 2.0 | Миграция оставшихся доменов, вывод маршрутов Camel, миграция отчётности из Power BI. Объём меньше, чем в Год 1 — основные риски уже отработаны. |
| **Потери от неэффективности** | 1.0 | Бизнес-аналитики работают в Self-Service BI Portal. Отчёты формируются за секунды. Остаточные потери — домены, ещё не полностью мигрированные. |
| **Итого Год 2** | **22.0** | |

### Год 3 (24–36 месяцев): целевое состояние

Legacy выведено (или остаётся минимально как read-only архив), целевая архитектура работает.

| Статья затрат | Сумма | Комментарий |
|--------------|-------|-------------|
| **Инфраструктура** (облако) | 3.5 | Только облачная инфраструктура. Managed Kafka, PostgreSQL, ClickHouse, K8s, S3. Автоскейлинг оптимизирует затраты. |
| **Лицензии** | 0.5 | Минимальные: Confluent Schema Registry (если коммерческая версия), возможные enterprise-фичи Grafana. Основной стек — open-source. |
| **Персонал** | 9.0 | Целевой состав: платформенная команда (~3 FTE), доменные инженеры (~5 FTE), Data Product Owners (совмещение с доменными ролями, ~1 FTE в пересчёте). Нет двойной нагрузки, нет legacy-специалистов. |
| **Эксплуатация** | 2.0 | Стабильная эксплуатация. Автоматизированный мониторинг, алертинг, self-healing (K8s). |
| **Проектные затраты** (финализация) | 0.5 | Финальный вывод legacy, архивация данных DWH, документация. |
| **Потери от неэффективности** | 0.5 | Минимальные: near-real-time отчётность, self-service, новые направления подключаются за дни. |
| **Итого Год 3** | **16.0** | |

### Итого to-be за 3 года: **67.0 у.е.**

## Точка окупаемости и прогноз

На горизонте 3 лет целевая архитектура **дороже** на 8.6 у.е. Это ожидаемо — первые два года параллельной работы стоят дорого. Однако:

**Год 3: экономия 5.0 у.е./год.** Целевая архитектура в стабильном состоянии стоит 16.0 у.е./год vs 21.0+ у.е./год для as-is (и as-is продолжает дорожать).

**Прогноз на Годы 4–5:**

| Год | As-Is (прогноз) | To-Be (прогноз) | Разница |
|-----|----------------|----------------|---------|
| Год 4 | ~22.5 | ~15.5 | **−7.0** |
| Год 5 | ~24.0 | ~15.5 | **−8.5** |

**Точка окупаемости (break-even):** приблизительно **на 4-м году** (через ~42 месяца). Начиная с этого момента, целевая архитектура дешевле as-is ежегодно, и разрыв нарастает.

**Накопленная экономия к концу 5-го года:** ~+6.9 у.е. в пользу целевой архитектуры.

## Неденежные факторы (качественная оценка)

TCO не учитывает ряд факторов, которые невозможно или некорректно выразить в деньгах, но которые критичны для решения:

| Фактор | As-Is | To-Be | Влияние |
|--------|-------|-------|---------|
| **Риск security-инцидента** (SQL Server 2008, end-of-life) | Высокий. Медицинские + финансовые данные без security patches. Один инцидент может стоить > всего TCO. | Низкий. Актуальные версии, managed-сервисы с автоматическим патчингом. | Критическое |
| **Time-to-market** (новые направления) | Месяцы. Каждое новое направление = изменения в DWH + Camel + координация. | Дни–недели. Новый BC подписывается на топики, не затрагивая существующие. | Высокое |
| **Масштабируемость** | Ограничена. Вертикальное масштабирование SQL Server дорого и имеет потолок. | Горизонтальная. Kafka, K8s, ClickHouse масштабируются линейно. | Высокое |
| **Привлечение и удержание кадров** | Сложно. PowerBuilder, SQL Server 2008, Camel — непривлекательный стек для рынка. | Проще. Kafka, K8s, Python, React — стек, на который есть спрос и предложение. | Среднее |
| **Регуляторные риски** | Растут. End-of-life ПО может не пройти аудит. | Снижаются. Актуальный стек, сертифицированный облачный провайдер. | Высокое |
| **Автономность команд** | Нет. Все зависят от DWH-команды. | Есть. Домены деплоятся независимо. | Высокое |

## Чувствительность (sensitivity analysis)

Ключевые допущения, при изменении которых TCO существенно меняется:

| Сценарий | Влияние на TCO to-be | Комментарий |
|----------|---------------------|-------------|
| Облачные тарифы +20% | +2.5 у.е. за 3 года | Инфраструктура — не основная статья. Влияние умеренное. |
| Миграция затягивается на 6 мес. | +4.0 у.е. за 3 года | Дополнительные полгода параллельной работы. Точка окупаемости сдвигается на ~6 мес. |
| Найм дороже на 30% | +3.0 у.е. за 3 года | Персонал — основная статья. Значительное влияние. |
| Security-инцидент на SQL Server 2008 | +10–50 у.е. (as-is) | Штрафы регуляторов, репутационный ущерб, юридические издержки. Делает as-is неприемлемым. |
| Отказ от 1 нового бизнес-направления (as-is) | +5–15 у.е. упущенной выручки/год (as-is) | Невозможность интеграции фармы/электроники → прямые потери выручки. |

## Выводы

1. **На горизонте 3 лет целевая архитектура дороже на ~15%.** Это плата за миграцию, параллельную работу двух миров и обучение команды.

2. **Точка окупаемости — 4-й год (~42 мес.).** После этого целевая архитектура экономит 5–8 у.е./год с нарастающим эффектом.

3. **Основной драйвер затрат — персонал (50%+ от TCO).** И в as-is, и в to-be. Разница: в as-is персонал дорожает (дефицит legacy-специалистов), в to-be — стабилизируется после миграции.

4. **Основной драйвер экономии — устранение неэффективности.** Потери от часовых отчётов, ручной сборки данных и невозможности self-service = 10.5 у.е. за 3 года в as-is vs 3.5 у.е. в to-be. Экономия 7.0 у.е.

5. **Неденежные факторы усиливают аргумент.** Риск security-инцидента на SQL Server 2008, невозможность масштабирования и потеря time-to-market — каждый из этих факторов в отдельности может перевесить разницу в TCO.

6. **Рекомендация: трансформация экономически обоснована,** особенно с учётом нарастающих рисков as-is и стратегических целей компании (масштабирование, новые направления, новые регионы).
