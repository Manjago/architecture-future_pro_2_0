# Стратегический роадмап внедрения Data Mesh «Будущее 2.0»

Роадмап описывает поэтапное внедрение Data Mesh в компании «Будущее 2.0»: этапы, ключевые роли, привязка к бизнес-целям и критерии перехода между этапами.

## Визуализация

![Roadmap](roadmap.png)

## Этапы внедрения

Три этапа, синхронизированные с общими этапами трансформации (из описания проекта) и TCO-анализом.

### Этап 1. Пилот (0–6 месяцев)

**Цель:** валидировать подход Data Mesh на 1–2 доменах, сформировать команду и стандарты.

| Направление | Действия |
|------------|----------|
| **Пилотные домены** | Billing (финансовые расчёты) и Patient Management (пациентский поток). Выбраны потому что: Billing — понятная доменная модель, чёткие события (InvoiceCreated, PaymentReceived); Patient Management — ключевой источник данных для других доменов, высокая бизнес-ценность витрины. |
| **Data Products** | Каждый пилотный домен публикует 1–2 data products: Billing → «Финансовые операции» (счета, платежи, агрегации по клиникам); Patient Management → «Пациентский поток» (регистрации, визиты, нагрузка на клиники). |
| **Платформа** | Развёртывание базовой Self-Serve Data Platform: Kafka + Schema Registry (Event Bus), Kafka Connect (Data Ingestion для пилотных доменов), ClickHouse (Analytics Store — пилот), Data Catalog (MVP — список доступных data products с описанием схем). |
| **Governance** | Формирование governance-группы: представители пилотных доменов + платформенная команда + ИБ. Определение стандартов: формат событий (Avro, стандартный конверт — уже описан в Task4), соглашения об именовании, минимальные SLA для data products. |
| **Legacy-мост** | Запуск Camel Bridge (ACL): трансляция данных из DWH в Event Bus для пилотных доменов. Параллельная работа: DWH продолжает обслуживать все остальные процессы. |
| **BI** | Прототип Self-Service BI Portal: аналитики пилотных доменов строят отчёты по data products из ClickHouse. Цель: показать бизнесу «отчёт за секунды вместо часов». |
| **Обучение** | Kafka (администрирование + разработка) — вся команда. DDD/Event Storming — доменные команды. Terraform + Kubernetes — DevOps. Внешние менторы на 3–6 мес. для code review и архитектурных консультаций. |

**Критерии перехода к Этапу 2:**
- Пилотные домены публикуют data products с SLA (freshness ≤ 30 сек, availability ≥ 99%).
- Бизнес-аналитики построили ≥ 5 отчётов в прототипе BI Portal.
- Camel Bridge стабильно работает (latency p95 < 500 мс, error rate < 0.1%).
- Governance-стандарты задокументированы и приняты governance-группой.
- Команда способна самостоятельно деплоить и поддерживать пилотные домены без внешних менторов.

### Этап 2. Масштабирование (6–18 месяцев)

**Цель:** распространить Data Mesh на критические домены, запустить полноценный портал самообслуживания, начать вывод legacy.

| Направление | Действия |
|------------|----------|
| **Новые домены** | Diagnostics, Credit, AI Diagnostics, Internal Operations → каждый формирует свой data product. Порядок подключения: Diagnostics и Credit (высокая бизнес-ценность, тесная связь с пилотными доменами), затем AI Diagnostics и Internal Operations. |
| **Data Products** | Каждый домен публикует 1–3 data products. Примеры: Diagnostics → «Исследования и результаты»; Credit → «Кредитный портфель»; AI Diagnostics → «Качество моделей» (метрики confidence, failure rate); Internal Operations → «Персонал и инвентаризация». |
| **Платформа** | Self-Service BI Portal — полноценный запуск (MVP → GA): Report Builder, Query Engine, Data Catalog (с поиском и фильтрацией), Access Control (RBAC по доменам). Apache Flink — потоковые трансформации для сложных аналитических проекций. MLflow — Model Registry для ИИ-домена. Jaeger/Zipkin — distributed tracing (correlationId). |
| **Governance** | Расширение governance-группы: представители всех доменов. Введение процесса согласования межсоменного доступа к данным. Мониторинг качества data products: автоматические проверки SLA, алерты при деградации. |
| **Legacy** | Поэтапный вывод маршрутов Camel: каждый мигрированный домен переключается на прямую работу с Event Bus. Power BI выводится: отчёты мигрируются в Self-Service BI Portal. DWH сохраняется для доменов, ещё не полностью мигрированных, но нагрузка снижается. ACL (Camel Bridge) сохраняется для оставшихся legacy-интеграций. |
| **Обучение** | Переквалификация legacy-специалистов: DBA → Data Engineer / Data Product Owner. PowerBuilder-разработчики → React-фронтенд (или уход с заменой). Внутренние хакатоны: команды строят data products и пайплайны в безопасной среде. |

**Критерии перехода к Этапу 3:**
- Все 7 bounded contexts публикуют data products.
- Self-Service BI Portal в продакшене, ≥ 80% регулярных отчётов мигрированы из Power BI.
- Бизнес-аналитики самостоятельно конструируют отчёты без помощи инженеров.
- Camel Bridge обслуживает только оставшиеся legacy-интеграции (нагрузка снижена ≥ 50%).
- Data Catalog содержит описания всех data products с актуальной документацией.
- Governance-процессы работают: SLA мониторятся автоматически, нарушения эскалируются.

### Этап 3. Зрелость и оптимизация (18–36 месяцев)

**Цель:** полный переход на Data Mesh, вывод legacy, подключение новых бизнес-направлений, доменная аналитика на потоках.

| Направление | Действия |
|------------|----------|
| **Новые направления** | Подключение фармацевтических компаний и производителя электроники как новых доменов. Каждый публикует свой data product по стандартным контрактам. Подключение занимает дни–недели (не месяцы), потому что платформа и стандарты уже есть. Подготовка к выходу в новые регионы: геораспределённое развёртывание, data residency. |
| **Data Products** | Зрелые data products с расширенными SLA. Введение tiering: Tier 1 (критичные, SLA 99.9%, freshness ≤ 10 сек) — финансовые и пациентские данные; Tier 2 (стандартные, SLA 99%, freshness ≤ 30 сек) — операционные данные; Tier 3 (best-effort) — экспериментальные и исследовательские данные. |
| **Платформа** | Оптимизация: автоскейлинг Kafka-кластера, оптимизация ClickHouse (materialized views, tiered storage). Self-Service BI Portal — расширенные функции: scheduled reports, алерты по метрикам, экспорт в PDF/Excel. Потоковая аналитика: реагирование на паттерны в реальном времени (аномалии в платежах, пики нагрузки). |
| **Governance** | Полная федеративная governance: governance-группа вырабатывает и пересматривает стандарты ежеквартально. Автоматизация compliance: проверка data products на соответствие регуляторным требованиям (медицинские данные не попадают в витрину, финансовые данные — audit trail). Data lineage: отслеживание происхождения данных от источника до отчёта. |
| **Legacy** | Полный вывод: PowerBuilder UI заменён React-based Web UI. Camel Bridge выключен: все интеграции через Event Bus. SQL Server 2008 → read-only архив (если требуется для исторических данных) или полностью выведен. Power BI полностью заменён Self-Service BI Portal. |
| **Организация** | Data Mesh как стандартный подход. Каждый новый домен стартует с data product by default. Data Product Owner — стандартная роль в каждой доменной команде. Платформенная команда фокусируется на развитии платформы, не на поддержке доменных данных. |

**Критерии достижения целевого состояния:**
- Legacy полностью выведено (SQL Server 2008, PowerBuilder, Camel ESB, Power BI).
- Все домены публикуют data products с автоматическим мониторингом SLA.
- Новое бизнес-направление подключается за ≤ 2 недели.
- Self-Service BI Portal — единственный инструмент аналитической отчётности.
- Слабосвязанная событийная платформа: домены взаимодействуют только через события.
- Готовность к геораспределённому развёртыванию (выход в новые регионы).

## Ключевые роли

| Роль | Когда появляется | Кто это | Ответственность |
|------|-----------------|---------|-----------------|
| **Data Product Owner** | Этап 1 (пилот) | Аналитик или PO домена, берущий дополнительную ответственность за данные. На старте — 2 DPO (по одному на пилотный домен). К Этапу 3 — DPO в каждом домене. | Определяет состав data product, устанавливает SLA, управляет бэклогом data product, участвует в governance-группе. |
| **Data Engineer (доменный)** | Этап 1 (пилот) | Инженер внутри доменной команды. На старте — переквалификация из бэкенд-разработчиков или DBA. На Этапе 2 — возможен целевой найм. | Строит пайплайны для публикации data product, поддерживает качество данных в домене, использует инструменты Self-Serve платформы. |
| **Platform Data Engineer** | Этап 1 (пилот) | Инженер платформенной команды. 2–3 человека, частично из текущей DevOps-команды, частично найм. | Развивает и поддерживает Self-Serve Data Platform (Kafka, Schema Registry, ClickHouse, Data Catalog, мониторинг). Создаёт шаблоны и инструменты для доменных команд. |
| **BI-аналитик** | Этап 1 (пилот) | Текущие бизнес-аналитики (~20 человек). Переход с Power BI на Self-Service BI Portal. | Строит отчёты и дашборды, использует Data Catalog для обнаружения данных, формулирует требования к data products. |
| **Governance Lead** | Этап 1 (пилот) | Архитектор или тимлид с кросс-доменным видением. 1 человек. | Координирует governance-группу, следит за соблюдением стандартов, эскалирует конфликты между доменами. |
| **Security Champion** | Этап 1 (пилот) | Специалист по ИБ, выделенный на проект миграции. | Аудит безопасности на каждом этапе, контроль compliance (ФЗ-152, требования ЦБ), проверка data residency. |

### Эволюция ролей

```
Этап 1 (0–6 мес.):
  2 Data Product Owner (пилотные домены)
  2 Data Engineer (доменных, пилотные домены)
  2–3 Platform Data Engineer
  ~5 BI-аналитиков (пилотная группа)
  1 Governance Lead
  1 Security Champion

Этап 2 (6–18 мес.):
  5–6 Data Product Owner (все критические домены)
  5–6 Data Engineer (доменных)
  3 Platform Data Engineer
  ~15 BI-аналитиков (масштабирование)
  1 Governance Lead
  1 Security Champion

Этап 3 (18–36 мес.):
  7+ Data Product Owner (все домены + новые направления)
  7+ Data Engineer (доменных)
  3 Platform Data Engineer
  ~20+ BI-аналитиков (все)
  1 Governance Lead
  Security — в штатном режиме (не выделенная роль)
```

## Привязка к бизнес-целям

| Бизнес-цель | Этап | Как адресуется |
|------------|------|---------------|
| **Архитектурное решение сформировано и согласовано** | Этап 1 (0–6 мес.) | C4-диаграммы (Task3), bounded contexts (Task4), техрадар и TCO (Task5) — уже готовы. Пилот валидирует решение на практике. |
| **Границы доменов определены, ключевые связи описаны** | Этап 1 (0–6 мес.) | 7 bounded contexts, Context Map, 15 доменных событий (Task4). Governance-группа фиксирует стандарты. |
| **Запланированы проекты по развитию витрины данных** | Этап 1 (0–6 мес.) | Пилотные data products (Billing, Patient Management). Прототип Self-Service BI Portal. |
| **Реализован портал самообслуживания** | Этап 2 (6–18 мес.) | Self-Service BI Portal в продакшене: Report Builder, Query Engine, Data Catalog, Access Control. |
| **Бизнес-пользователи работают с данными в новой архитектуре** | Этап 2 (6–18 мес.) | Все домены публикуют data products. BI-аналитики строят отчёты в портале. ≥ 80% отчётов мигрированы. |
| **Запуск новых финтех- и медицинских сервисов** | Этап 3 (18–36 мес.) | Новые сервисы стартуют как data products by default. Подключение через стандартные контракты. |
| **Выход в новые регионы** | Этап 3 (18–36 мес.) | Геораспределённое развёртывание, data residency, Kafka мульти-DC репликация. |
| **Near-real-time обработка данных** | Этап 2–3 | Data products обновляются через события (секунды). Потоковая аналитика на Этапе 3. |
| **Слабосвязанная событийная платформа** | Этап 3 (18–36 мес.) | Все домены через события, legacy выведено, Camel и DWH — не используются. |

## Риски роадмапа

Основные риски описаны в карте рисков (Task3, [`risk-map.md`](../Task3Advanced/risk-map.md)). Здесь — специфичные для роадмапа Data Mesh:

| Риск | Вероятность | Влияние | Мера |
|------|------------|---------|------|
| Пилот не подтверждает подход (данные не ложатся в data product) | Низкая | Высокое | Выбраны домены с чёткой моделью (Billing, Patient Mgmt). Откат к Этапу 0 — дёшево (6 мес. работы). |
| Бизнес не видит ценности после пилота | Средняя | Высокое | Демо-сессии, конкретные метрики: «отчёт за 5 секунд вместо 3 часов». Вовлечение бизнеса с Этапа 1. |
| Data Product Owner перегружены (совмещение ролей) | Средняя | Среднее | На Этапе 1 — минимальный scope (1–2 data products). На Этапе 2 — оценка нагрузки, при необходимости выделение DPO как полной роли. |
| Платформенная команда — bottleneck | Средняя | Высокое | Self-Serve подход: шаблоны, документация, инструменты. Доменные команды не зависят от платформы для типовых операций. |
| Governance замедляет доставку | Низкая | Среднее | Lightweight governance на старте: минимум обязательных стандартов, остальное — рекомендации. Усиление по мере зрелости. |
