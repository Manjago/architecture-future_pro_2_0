## Детальный план по каждому риску

### R1. Неверная декомпозиция на домены

**Уровень:** Высокий | **Стратегия:** Снижение | **Тип мер:** Технические + Управленческие

**Триггеры (как понять, что риск реализуется):**
- Частые синхронные вызовы между доменами (> 3 sync-зависимостей между двумя доменами)
- Изменение в одном домене требует синхронного деплоя другого
- При удалении подписчика ломается продюсер

**Меры снижения:**

*Технические:*
- Провести Event Storming до начала реализации — выявить реальные доменные события и границы
- Начать с пилота в 1–2 доменах (финансовые расчёты и/или пациентский поток), валидировать границы на практике
- Contract testing между доменами — автоматическая проверка, что контракты событий соблюдаются
- Мониторинг межсоменных вызовов: если появляются sync-зависимости — пересмотреть границы

*Управленческие:*
- Архитектурные review на каждом этапе с участием представителей всех доменов
- Итеративный подход: границы уточняются по мере набора опыта, а не фиксируются раз и навсегда

---

### R2. Eventual consistency не принята бизнесом

**Уровень:** Средний | **Стратегия:** Снижение | **Тип мер:** Управленческие

**Триггеры:**
- Бизнес-пользователи жалуются на «неактуальные данные» в отчётах
- Требования «хотим как раньше, мгновенно» от аналитиков
- Попытки обойти event-driven архитектуру прямыми запросами к БД других доменов

**Меры снижения:**

*Управленческие:*
- Провести демо-сессии для бизнеса: показать, что «раньше отчёт собирался 3 часа, теперь данные отстают на 5 секунд» — это объективное улучшение
- Зафиксировать SLA на задержку данных в витрине (например, ≤ 30 секунд для стандартных отчётов)
- Обучение бизнес-аналитиков: что такое eventual consistency, почему это нормально, как проектировать отчёты с учётом этого
- В UI портала показывать timestamp последнего обновления данных — прозрачность снимает тревогу

### R3. Vendor lock-in на облачного провайдера

**Уровень:** Средний | **Стратегия:** Избежание | **Тип мер:** Технические

**Триггеры:**
- Более 50% инфраструктуры использует проприетарные API провайдера без абстракций
- Оценка стоимости миграции на другого провайдера превышает 6 месяцев работы

**Меры снижения:**

*Технические:*
- Использовать open-source технологии там, где возможно: Apache Kafka (не проприетарный брокер провайдера), PostgreSQL (не проприетарная СУБД), Keycloak (не проприетарный IAM)
- Terraform как IaC — cloud-agnostic, при смене провайдера переписываются конфигурации, а не архитектура
- Абстракции на уровне приложений: не использовать напрямую SDK провайдера в бизнес-логике, выносить в инфраструктурный слой
- Контейнеризация (Kubernetes) — приложения не привязаны к конкретному compute-сервису

### R4. ACL / Camel Bridge становится bottleneck

**Уровень:** Критический | **Стратегия:** Снижение | **Тип мер:** Технические

**Триггеры:**
- Latency на Camel Bridge > 500ms (p95)
- Очередь необработанных сообщений на bridge растёт
- Инциденты с даунтаймом bridge, затрагивающие бизнес-процессы

**Меры снижения:**

*Технические:*
- Нагрузочное тестирование Camel Bridge до запуска: смоделировать реальный объём трафика между legacy и event bus
- Горизонтальное масштабирование: несколько инстансов Camel Bridge с балансировкой нагрузки
- Поэтапный вывод интеграций через bridge: каждый домен по мере готовности переключается на прямую работу с event bus, снижая нагрузку на bridge
- Circuit breaker на bridge: при деградации — graceful degradation, а не каскадный сбой
- Мониторинг и алертинг: throughput, latency, error rate, размер очередей на bridge
- Параллельные каналы: для критичных потоков (финансовые операции) рассмотреть отдельный инстанс bridge с выделенными ресурсами

### R5. Потеря или искажение данных при миграции DWH

**Уровень:** Высокий | **Стратегия:** Снижение | **Тип мер:** Технические

**Триггеры:**
- Расхождения в count/sum между DWH и новым хранилищем после тестовой миграции
- Обнаружение недокументированных хранимых процедур/триггеров, влияющих на данные
- Бизнес-пользователи замечают несоответствия в отчётах после миграции

**Меры снижения:**

*Технические:*
- Полный аудит DWH до начала миграции: инвентаризация таблиц, views, хранимых процедур, триггеров, jobs. Документирование неявной бизнес-логики
- Тестовая миграция на staging-среде: прогнать полный цикл миграции, сверить данные
- Parallel run: старая и новая системы работают одновременно, данные автоматически сверяются (reconciliation jobs)
- Поэтапная миграция по доменам: сначала наименее критичные данные (инвентаризация, HR), потом финансовые, медицинские — в последнюю очередь
- Rollback-план: возможность отката на DWH на каждом этапе
- CDC (Change Data Capture): для синхронизации данных между DWH и новыми хранилищами в переходный период

### R6. Производительность Event Bus не подтверждена

**Уровень:** Средний | **Стратегия:** Снижение | **Тип мер:** Технические

**Триггеры:**
- Consumer lag растёт при увеличении числа доменов/событий
- Latency end-to-end > SLA (например, > 5 секунд для витрины данных)
- Kafka-кластер требует незапланированного масштабирования

**Меры снижения:**

*Технические:*
- Capacity planning до запуска: рассчитать expected throughput (количество событий/сек по доменам, средний размер сообщения, число консюмеров)
- Нагрузочное тестирование на staging: смоделировать пиковую нагрузку (×2–3 от expected), замерить latency и throughput
- Правильное партиционирование: ключи партиций по доменам / агрегатам для равномерной нагрузки
- Мониторинг: consumer lag, broker disk usage, network throughput — алерты при приближении к порогам
- План масштабирования: managed Kafka в облаке позволяет добавлять брокеры и партиции, иметь готовый runbook

### R7. Безопасность при миграции

**Уровень:** Высокий | **Стратегия:** Снижение | **Тип мер:** Технические + Управленческие

**Триггеры:**
- Обнаружение незашифрованных данных в промежуточных хранилищах
- Расширение сетевого периметра без обновления firewall-правил
- Результаты пентеста показывают новые уязвимости

**Меры снижения:**

*Технические:*
- Шифрование данных at rest и in transit на всех этапах миграции (TLS, envelope encryption)
- Минимизация промежуточных сред: данные не копируются в временные хранилища без необходимости
- Сетевая изоляция: VPC, private subnets, security groups — новая инфраструктура не открыта в публичный интернет
- Логирование и аудит: все операции с чувствительными данными логируются, доступ по принципу least privilege
- Маскирование/анонимизация данных в dev/staging-средах

*Управленческие:*
- Аудит безопасности на каждом этапе миграции
- Пентест до и после миграции каждого критичного компонента
- Назначить ответственного за информационную безопасность миграции (Security Champion)

---

### R8. Нехватка компетенций по новому стеку

**Уровень:** Высокий | **Стратегия:** Снижение | **Тип мер:** Управленческие

**Триггеры:**
- Сроки задач по новому стеку систематически превышают оценку (×2 и более)
- Архитектурные ошибки, вызванные непониманием инструментов (неправильное партиционирование Kafka, ошибки в Terraform)
- Зависимость от 1–2 человек, знающих новый стек

**Меры снижения:**

*Управленческие:*
- План обучения до начала реализации: Kafka (администрирование + разработка), Kubernetes, Terraform, observability-стек
- Внутренние хакатоны: команда строит пилотный pipeline на новом стеке в безопасной среде
- Менторинг: привлечь внешних экспертов на первые 3–6 месяцев для code review и архитектурных консультаций
- Парное владение: минимум два человека на каждую критичную технологию (bus factor)
- Пилотный проект на некритичном домене: команда набирает опыт на реальной задаче без риска для бизнеса
- Найм: если gap слишком большой — целевой найм 2–3 специалистов с опытом Kafka/K8s

### R9. Сопротивление изменениям

**Уровень:** Высокий | **Стратегия:** Снижение | **Тип мер:** Управленческие

**Триггеры:**
- Ключевые специалисты по DWH/ESB начинают увольняться
- Скрытый саботаж: задачи по новой архитектуре систематически деприоритизируются
- На meeting-ах звучит «у нас всё работало, зачем трогать» без конструктивного диалога

**Меры снижения:**

*Управленческие:*
- **Вовлечение legacy-экспертов в проектирование.** Команда DWH/ESB — ключевые участники Event Storming, архитектурных review, проектирования ACL. Их знание неявной бизнес-логики — актив, а не балласт. Формат: не «мы вам расскажем, как будет», а «без вас мы не понимаем, как работает текущая система»
- **Переквалификация с конкретной карьерной перспективой.** Не абстрактное «мы вас обучим», а конкретный план: DWH-инженер → Data Product Owner или инженер data pipeline. Доменная экспертиза сохраняется, меняется инструментарий. Каждый специалист получает персональный план развития с timeline
- **Быстрые победы.** Пилот на одном домене, где новый подход даёт наглядный результат (отчёт за секунды вместо часов). Когда люди видят выигрыш — сопротивление снижается органически
- **Прозрачная коммуникация.** Честный роадмап: «DWH не выключится завтра, legacy живёт ещё 18–36 месяцев, переход постепенный». Регулярные демо для всей команды — прозрачность по статусу и планам. Неопределённость порождает страх, прозрачность снижает его
- **Коалиция сторонников.** Найти 2–3 неформальных лидера в команде, которые видят ценность в трансформации, и опереться на них как на амбассадоров изменений

### R10. Двойная нагрузка на команду

**Уровень:** Высокий | **Стратегия:** Снижение | **Тип мер:** Управленческие

**Триггеры:**
- Рост числа инцидентов в legacy-системах из-за недостатка внимания
- Срыв сроков по новым компонентам
- Увеличение текучки кадров, жалобы на переработки

**Меры снижения:**

*Управленческие:*
- Выделенные команды: разделить людей на «поддержка legacy» и «строительство нового», минимизировать контекст-свитчинг. Не один человек на два фронта, а чёткое разделение
- Приоритизация: на этапе миграции сознательно снизить объём нового функционала в legacy. Только critical bugfix, никаких новых фич в DWH
- Поэтапное сокращение legacy: каждый домен, мигрировавший на новую архитектуру, снижает нагрузку на legacy-команду. Важно, чтобы это было видимо для людей — «вот, мы уже выключили этот кусок»
- Найм на переходный период: если бюджет позволяет — усилить команду на 18 месяцев параллельной жизни
- Мониторинг выгорания: регулярные 1-on-1, отслеживание переработок, возможность ротации между командами

### R11. Регуляторные нарушения при миграции

**Уровень:** Средний | **Стратегия:** Избежание | **Тип мер:** Управленческие + Технические

**Триггеры:**
- Регулятор запрашивает документацию по хранению/обработке данных, а она не готова
- Облачный провайдер не имеет нужных сертификаций
- При выходе в новый регион обнаруживаются неучтённые требования к локализации данных

**Меры снижения:**

*Управленческие:*
- Аудит регуляторных требований до начала миграции: ФЗ-152, требования ЦБ, отраслевые стандарты. Привлечь юристов, специализирующихся на healthtech и fintech
- Проверка сертификаций облачного провайдера: соответствие требованиям по хранению медицинских и финансовых данных
- При планировании выхода в новые регионы — предварительный анализ локальных требований (GDPR, местные аналоги)

*Технические:*
- Data residency: чувствительные данные хранятся в юрисдикции, соответствующей требованиям регуляторов
- Разделение данных: медицинские карты и истории болезни не попадают в витрину данных (уже заложено в архитектуру)
- Логирование и аудит: полный audit trail для операций с чувствительными данными

---

### R12. Превышение бюджета и сроков

**Уровень:** Высокий | **Стратегия:** Снижение | **Тип мер:** Управленческие

**Триггеры:**
- Фактические затраты превышают план на > 15% по итогам этапа
- Более 30% задач не укладываются в оценку
- Обнаружение крупных незапланированных работ (например, переписывание 200 хранимых процедур)

**Меры снижения:**

*Управленческие:*
- Бюджетный буфер 25–30% к первоначальной оценке — стандартная практика для проектов с legacy-миграцией
- Поэтапная оценка: не пытаться оценить весь проект на 3 года вперёд, а переоценивать на каждом этапе (0–6, 6–18, 18–36 месяцев)
- Контрольные точки (milestones) с go/no-go решениями: после пилота — пересмотр оценок перед масштабированием
- Прозрачный трекинг затрат: облачные расходы, лицензии, ФОТ, внешние консультанты — всё в одном дашборде
- Scope management: при угрозе превышения бюджета — пересмотр приоритетов, а не попытка «успеть всё»

## Мониторинг и пересмотр

Карта рисков — живой документ. Рекомендуемый ритм пересмотра:

- **Еженедельно:** проверка триггеров по критическим рискам (R4), мониторинг технических метрик
- **Ежемесячно:** пересмотр всех высоких рисков, обновление вероятностей и мер
- **На каждом milestone (этап трансформации):** полный пересмотр карты, добавление новых рисков, закрытие реализовавшихся или неактуальных
