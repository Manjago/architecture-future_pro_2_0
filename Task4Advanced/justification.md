# Обоснование событийного подхода vs Camel/DWH

## Контекст

Компания «Будущее 2.0» сейчас строит интеграцию между системами на двух механизмах:

1. **DWH (SQL Server 2008)** — центральное хранилище, в котором сосредоточена значительная часть бизнес-логики (хранимые процедуры, views, триггеры). DWH выступает не только как аналитическое хранилище, но и как интеграционный хаб: данные из разных подсистем стекаются в DWH, трансформируются там и раздаются потребителям.

2. **ESB на Apache Camel** — сервисная шина, через которую проходят потоки данных между ИИ-сервисами, финтех-сервисами, внутренними сервисами и DWH.

Предлагаемая целевая архитектура заменяет оба механизма на **событийную интеграцию через Apache Kafka (Event Bus)**, где домены взаимодействуют через доменные события, а Camel и DWH остаются только как мосты совместимости на переходный период.

Ниже — обоснование этого решения.

---

## Проблемы текущей архитектуры

### DWH как интеграционный хаб

**Проблема:** DWH выполняет две принципиально разные функции — аналитическое хранилище и интеграционный слой. Бизнес-логика, которая должна принадлежать доменам, живёт в хранимых процедурах SQL Server 2008.

**Последствия:**
- Любое изменение бизнес-логики одного домена требует изменения хранимых процедур в DWH, тестирования и деплоя всей системы.
- Невозможно добавить новое бизнес-направление (фармкомпании, производитель электроники) без модификации DWH.
- Формирование сложных отчётов занимает часы — DWH перегружен и транзакционными, и аналитическими запросами.
- SQL Server 2008 — end-of-life с 2019 года, без обновлений безопасности.
- Сотни терабайт данных в одном хранилище — масштабирование дорогое и ограниченное.

### ESB на Apache Camel

**Проблема:** Camel используется как point-to-point интеграция — маршруты жёстко связывают конкретные системы. При добавлении нового потребителя нужно создавать новый маршрут.

**Последствия:**
- Тесная связность: изменение формата данных на одной стороне ломает маршрут на другой.
- Camel-маршруты — синхронные по своей природе. При недоступности потребителя — сбой всей цепочки.
- Нет единой схемы данных — каждый маршрут транслирует данные по-своему.
- Масштабирование ограничено: увеличение числа маршрутов линейно увеличивает сложность поддержки.
- Нет replay: если потребитель пропустил данные из-за сбоя — данные потеряны.

### Общие проблемы

- **Bottleneck на двух компонентах.** И DWH, и Camel — единые точки отказа. Сбой любого из них затрагивает все подсистемы.
- **Time-to-market.** Подключение нового бизнес-направления требует изменений в DWH + новых маршрутов в Camel + координации между командами. Это недели и месяцы вместо дней.
- **Невозможность автономной разработки.** Все команды зависят от DWH-команды и расписания деплоев центрального хранилища.

## Что даёт событийный подход

### 1. Слабая связность между доменами

**Было:** Домен A → маршрут Camel → DWH → маршрут Camel → Домен B. Изменение в A требует координации с DWH и B.

**Стало:** Домен A публикует событие `PatientRegistered` в Event Bus. Домен B подписан на это событие и обрабатывает его самостоятельно. A не знает о существовании B.

**Преимущество:** домены развиваются и деплоятся независимо. Добавление нового подписчика — это подписка на топик, без изменения продюсера.

### 2. Масштабируемость при добавлении бизнес-направлений

**Цель бизнеса:** интеграция фармкомпаний, производителя электроники, выход в новые регионы.

**Текущая архитектура:** каждое новое направление = новые таблицы в DWH + новые хранимые процедуры + новые маршруты Camel + координация со всеми затронутыми командами.

**Событийная архитектура:** новое направление = новый Bounded Context со своей БД, публикующий события в Event Bus. Существующие домены не затрагиваются. Analytics подписывается на новые события автоматически через Data Ingestion.

### 3. Переход от batch к near-real-time

**Было:** Отчётность формируется batch-процессами в DWH. Сложные отчёты занимают часы. Данные для аналитики актуальны «по состоянию на вчера».

**Стало:** Доменные события поступают в Analytics Store в реальном времени через Kafka + Data Ingestion (Kafka Connect / Flink). Данные актуальны с задержкой в секунды (SLA ≤ 30 секунд для стандартных отчётов).

**Преимущество:** бизнес-аналитик видит актуальную картину, а не вчерашний срез. Это объективное улучшение по сравнению с часовыми batch-отчётами, даже с учётом eventual consistency.

### 4. Устойчивость к сбоям

**Было:** Camel-маршрут — синхронный. Если потребитель недоступен, данные теряются или копятся в очереди Camel (ограниченной).

**Стало:** Kafka — распределённый лог с configurable retention. Если потребитель упал, сообщения сохраняются в топике. Потребитель при восстановлении читает с последнего offset. Данные не теряются.

**Дополнительно:** DLQ (Dead Letter Queue) для событий, которые потребитель не смог обработать. Schema Registry — валидация формата на уровне инфраструктуры.

### 5. Автономность доменов

**Было:** Все команды зависят от DWH-команды. График деплоев — узкое место. Изменение в финтех-модуле требует проверки медицинских отчётов — всё связано через общие хранимые процедуры.

**Стало:** Каждый домен владеет своими данными, своей БД, своими сервисами. Межсоменное взаимодействие — только через события (fire-and-forget). Внутри домена — синхронные вызовы (REST/gRPC). Домен деплоится независимо. Контракт фиксируется через Avro-схемы в Schema Registry.

**Преимущество:** финтех-команда может деплоить ежедневно, не координируясь с медицинским доменом. Это критично для компании с четырьмя юридически отдельными подразделениями.

### 6. Поддержка новых сценариев

Событийная архитектура открывает сценарии, невозможные с текущим стеком:

- **Event Sourcing** — для финансовых операций (полный audit trail, требование регуляторов).
- **CQRS** — разделение моделей чтения и записи, оптимизация аналитических запросов.
- **Потоковая аналитика** — реагирование на паттерны в реальном времени (аномалии в платежах, пики нагрузки на клиники).
- **Data Mesh** — домены как data products, каждый публикует события с гарантиями качества. Основа для Self-Service BI.

## Сравнительная таблица

| Критерий | Текущее (Camel + DWH) | Целевое (Event Bus) |
|----------|----------------------|-------------------|
| **Связность** | Тесная (point-to-point через Camel, общие процедуры в DWH) | Слабая (fire-and-forget через события) |
| **Добавление домена** | Недели/месяцы (DWH + Camel + координация) | Дни (новый BC, подписка на топики) |
| **Актуальность данных** | Часы (batch) | Секунды (near-real-time) |
| **Устойчивость к сбоям** | Потеря данных при сбое потребителя | Replay из Kafka, DLQ |
| **Автономность команд** | Все зависят от DWH-команды | Каждый домен независим |
| **Масштабирование данных** | Вертикальное (мощнее SQL Server) | Горизонтальное (партиции Kafka, шардинг) |
| **Схемы данных** | Неявные (хранимые процедуры, маршруты) | Явные (Avro + Schema Registry, версионирование) |
| **Мониторинг интеграций** | Ручной (логи Camel, SQL Profiler) | Централизованный (consumer lag, throughput, DLQ) |
| **Поддержка стека** | SQL Server 2008 (end-of-life) | Kafka, ClickHouse, PostgreSQL (активно развиваются) |

## Риски перехода и как мы их адресуем

Переход на событийную архитектуру — не бесплатный. Основные риски описаны в карте рисков (Task3, [`risk-map.md`](../Task3Advanced/risk-map.md)), здесь — краткая сводка по рискам, специфичным для EDA:

| Риск | Мера |
|------|------|
| Eventual consistency непривычна бизнесу | SLA на задержку (≤ 30 сек), демо-сессии, прозрачность в UI |
| Camel Bridge — bottleneck на переходном этапе | Нагрузочное тестирование, горизонтальное масштабирование, поэтапный вывод |
| Потеря данных при миграции DWH | Тестовая миграция, parallel run, CDC |
| Сложность отладки распределённых систем | correlationId для сквозной трассировки, централизованный logging, distributed tracing (Jaeger/Zipkin) |
| Ordering guarantee | Партиционирование по ключу агрегата — события одного агрегата обрабатываются строго по порядку |

## Почему не оставить Camel + модернизировать DWH?

Альтернативный вариант — обновить SQL Server до актуальной версии, оптимизировать хранимые процедуры, добавить новые маршруты в Camel для каждого нового направления.

**Почему этот вариант не работает:**

1. **Бизнес-логика останётся в DWH.** Даже с новой версией SQL Server проблема тесной связности не решается. Добавление фармкомпаний и производителя электроники снова потребует модификации центрального хранилища.

2. **Point-to-point масштабируется плохо.** При N доменах количество потенциальных маршрутов Camel — O(N²). С текущими 5 доменами это терпимо. С 10 доменами (после интеграции фармы, электроники, новых регионов) — неуправляемо.

3. **Batch останется batch.** Даже обновлённый DWH не даст near-real-time без фундаментального изменения подхода к интеграции.

4. **Не решает цель на 3 года.** Целевая архитектура — слабосвязанная событийная платформа с доменной аналитикой на потоках. Camel + DWH архитектурно неспособны это обеспечить.

## Выводы

Событийный подход — это не «модная замена» Camel и DWH. Это **архитектурное решение**, которое напрямую адресует бизнес-цели «Будущего 2.0»:

- **Портал самообслуживания** → возможен благодаря near-real-time обновлению данных через события и независимости аналитического домена.
- **Интеграция новых направлений без изменения DWH** → домены публикуют события, не модифицируя центральное хранилище.
- **Масштабирование на новые регионы** → автономные домены с геораспределённым развёртыванием, Kafka поддерживает мульти-DC репликацию.
- **Слабосвязанная платформа через 3 года** → события как единственный контракт между доменами, Camel и DWH выведены.

Переход поэтапный: пилот в 1–2 доменах (0–6 мес.), расширение (6–18 мес.), полный переход (18–36 мес.). На каждом этапе — возможность пересмотра, откат к legacy при необходимости, измеримые критерии успеха.
